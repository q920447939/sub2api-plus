## 0. 一句话定位

**先把邮箱变成「可信的触达渠道」，再在上面做召回和资讯推送。**
没有验证过的邮箱，发营销邮件会产生大量退信和垃圾举报，拉低发信域名信誉，最后连验证码、密码重置这类关键邮件也进了垃圾箱。所以「补验证」是「触达中心」的前提。同时，「验证邮箱领积分」本身就是第一次召回：它只发给充值过的老客户。

## 2. 目标与衡量指标

| 目标 | 指标 |
|---|---|
| 邮箱可信 | 充值过的用户中已验证的比例（目标：上线 30 天内 ≥ 70%） |
| 发得出去 | 发送成功率 ≥ 98%；退信率 < 2%；退订率 < 0.5%/封 |
| 召得回来 | 验证邀请和召回邮件发出后，7 天内登录率、14 天内充值率 |
| 不打扰用户 | 每个用户每 7 天最多收到 1 封营销类邮件；投诉为 0 |

## 3. 模块 A：邮箱验证补齐

### 3.1 邮箱状态模型

用户表新增 `email_verified_at`（可空时间）和 `email_invalid_at`（可空时间，硬退信时写入）。

| 状态 | 判定 | 用户看到什么 |
|---|---|---|
| 免验证 | `role = admin` | 不显示任何验证提示，不受强制验证限制 |
| 已验证 | `email_verified_at` 不为空 | 资料页显示「已验证」 |
| 待验证 | `email_verified_at` 为空 | 横幅提示去验证 |
| 无效 | `email_invalid_at` 不为空（发信硬退信，即地址不存在） | 提示「邮箱无法接收邮件，请更换」，并从所有发送名单中排除 |

### 3.2 管理员豁免（硬性要求）

管理员一律**免验证**，判定只看角色，不靠给管理员写一个假的 `email_verified_at`：
- 强制验证（3.7）在任何档位下都**不拦截**管理员，保证管理员始终能登录后台处理问题。
- 不给管理员显示横幅，不发验证奖励。
- 验证覆盖率等统计不计入管理员。
- 人群圈选默认排除管理员。
- 管理员也可以主动验证自己的邮箱（资料页入口保留），但不是必须的。

### 3.3 存量数据

上线时**不做回填**：除管理员外，所有存量用户的状态都是「待验证」。

### 3.4 新增数据的规则

- **上线时打开注册邮箱验证**（`email_verify_enabled = true`）。注册时输对验证码的新用户，`email_verified_at` 写入注册时间。
- 以后所有能证明邮箱归属的动作（输对验证码、点击邮件里的验证链接、成功重置密码）都会写入 `email_verified_at`。
- 用户修改邮箱后，状态重置为「待验证」。
- 管理员在后台手动创建的用户为「待验证」，用户登录后自行验证。

### 3.5 用户端验证流程

**入口：**
1. 登录后顶部横幅。有奖励资格的用户看到「验证邮箱，领取 N 积分」；没有资格的用户看到「验证邮箱，及时收到余额和订阅提醒」。横幅可以关闭，关闭后 7 天内不再显示。
2. 个人资料页的邮箱一栏：状态标签 +「去验证」按钮。
3. 验证邀请邮件里的链接（见 3.6）。

**流程（在弹窗里完成，不跳页）：**
```
显示当前邮箱 ──→ [邮箱正确] 发送验证码 → 输入验证码 → 验证成功 → 发放奖励 + 提示
              └→ [邮箱填错了/不用了] 输入新邮箱 → 发验证码到新邮箱 → 验证成功后替换邮箱
```
- 必须允许「换邮箱」：验证从未开启过，很多人注册时随手填了错的或不常用的邮箱。新邮箱要做唯一性检查和后缀白名单检查（复用 `registration_email_suffix_whitelist`）。
- 邮箱就是登录账号，换邮箱成功后明确提示「下次请用新邮箱登录」。
- 验证码限流沿用现有的冷却规则。

**奖励（同时也是召回手段）：**
- 资格：**充值过的老用户**，判定条件为 `total_recharged > 0`。充值的主要方式是兑换码，管理员手动加余额（包括线下收款后操作）也会累加这个字段，两者都算充值过，符合实际业务逻辑。
- **新用户不发奖励**：新注册用户完成验证是正常注册流程的一部分，不单独发积分。
- 奖励金额固定为 **200 积分**，在后台可修改，设为 0 即关闭。
- 每个用户只能领一次，换邮箱后再验证不会重复发。新增积分来源 `email_verify_reward`。

### 3.6 验证邀请邮件

后台可以对「待验证」用户群发验证邀请，邮件里是一个**一次性验证链接**（有效期 7 天），点击即完成验证、登录后奖励到账。
- 点了链接本身就证明邮箱有效，比让用户回站点输验证码的转化率高。
- 这封邮件同时也是一次**名单清洗**：硬退信的地址会被标为「无效」。
- 文案分两个版本：给充值过的用户的版本写明奖励积分（这就是第一波召回）；给其他用户的版本只讲验证的好处。
- 属于服务类邮件，但仍然带退订链接（降低被举报为垃圾邮件的概率）。
- **分批发送**：因为整个名单从未验证过，无效地址的比例未知。建议第一批只发最近 90 天活跃的充值用户，退信率正常之后再扩大范围；退信率超过阈值时自动暂停（见 4.4）。

### 3.7 强制程度（后台可配置，分三档）

| 档位 | 行为 | 分期 |
|---|---|---|
| 仅提示（默认） | 只显示横幅和资料页标签 | V1 |
| 关键操作前提示 | 充值、开通订阅、修改密码前弹窗提醒，可跳过 | V2 |
| 截止日期后强制 | 截止日期后，未验证的用户登录后必须先验证或换邮箱，才能使用控制台 | V2 |

强制验证的规则：
- **管理员任何时候都不受影响**（见 3.2）。
- **只拦截网页控制台，不拦截 API 调用**。用户已经配置好的 API Key 照常工作，否则付费用户的程序会在没有任何提示的情况下中断，引起投诉和流失。
- 截止期限为 **7 天**，在后台可配置。开启强制验证时，从当天 0 点起算 7 天后进入强制状态；在到期前通过站内公告和邮件（发给邮箱状态正常的用户）提醒用户尽快验证，到期前 3 天再提醒一次。
- 邮箱被标为「无效」的用户，强制页面直接引导去换邮箱。
- **建议先在「仅提示」档位运行一轮验证邀请，待充值老用户的验证率明显提升后再开启强制验证**，避免大量付费用户在 7 天内被锁在控制台外。

## 4. 模块 B：邮件触达中心

### 4.1 邮件分类（决定退订规则和发送优先级）

| 类别 | 例子 | 能否退订 | 发给谁 |
|---|---|---|---|
| 服务类 | 验证邀请、强制验证通知、条款变更、重要服务调整 | 不能退订分类，但仍然带退订链接；内容必须和服务相关 | 所有状态非「无效」的邮箱 |
| 资讯类 | 新模型上线、功能更新、月度简报 | 可单独退订 | 仅已验证 |
| 召回类 | 「好久不见，送你 X 积分」 | 可单独退订 | 仅已验证 |
| 活动类 | 节日充值优惠 | 可单独退订 | 仅已验证 |

用户在资料页的「邮件订阅偏好」里可以分别开关资讯、召回、活动三类。退订链接复用现有机制，营销类邮件同时带 `List-Unsubscribe` 和 `List-Unsubscribe-Post` 邮件头（Gmail、Yahoo 对批量发件人要求一键退订）。

> 现有的系统通知邮件（余额不足、订阅到期等）不受影响，继续按原有逻辑发送。

### 4.2 人群圈选

管理员用条件组合定义目标人群，可以保存为「人群模板」重复使用。

**可用条件：**
- 账号：注册时间、用户状态、所在分组（管理员始终排除）
- 活跃：最近登录时间、最近活跃（调用 API）时间
- 付费：累计充值金额、当前余额、是否充值过
- 订阅：有生效订阅 / 订阅已过期 N 天内 / 从未订阅
- 邮箱：验证状态（营销类只能选已验证）
- 触达：最近 N 天是否收到过营销邮件、是否退订了该类别

**预置人群：**

| 人群 | 条件 | 推荐内容 |
|---|---|---|
| 待验证老客 | 充值过、待验证 | 验证邀请（带奖励），即第一波召回 |
| 沉默老客 | 充值过、已验证、30 天未活跃 | 召回 + 积分 |
| 余额沉睡 | 余额 > 0、已验证、14 天未活跃 | 提醒「你还有 ¥X 余额」 |
| 订阅流失 | 订阅过期 7 到 30 天、已验证、没有续费 | 续费提醒 |
| 全体已验证用户 | 已验证、没有退订资讯类 | 资讯简报 |

圈选完成后显示**预计人数**和**排除明细**（例如「已退订 120 人，7 天内收过邮件 80 人，邮箱未验证 300 人」），并且可以抽查 20 个样本用户。

### 4.3 内容编辑

- Markdown 编辑 + 实时预览（复用反馈中心的 Markdown 组件和图片能力），系统套用统一的邮件外框（站点 logo、页脚、退订链接）。
- 变量：`{username}` `{balance}` `{site_name}` `{last_active_days}` `{expire_date}` `{reward_points}`，没有值时使用后台设置的默认值。主题行和正文都支持变量。
- 多语言：按用户的语言偏好发送对应版本，没有对应版本时使用默认语言。
- **附带积分**（召回类的核心）：活动可以设置「领取积分 N」。邮件里的领取链接是每个人独立的，**用户点击后登录才到账**，这样没打开邮件的人不会白拿，也方便统计转化。积分来源新增 `outreach_reward`，同一活动每人只能领一次，只有发送快照里的用户能领。
- 同步站内公告（可选）：资讯类可以勾选「同时发布站内公告」，覆盖还没验证邮箱的用户。

### 4.4 发送

- **先测试后发送**：必须先给自己发一封测试邮件，才能开放「正式发送」按钮。
- **发送方式**：立即发送 / 定时发送。
- **限速队列**：后台配置每分钟、每小时、每天的发送上限（适配 SMTP 服务商的限额），超出部分自动顺延。
- **频控**：
  - 同一用户每 7 天最多收到 1 封营销类邮件（全局，可配置）。
  - 同一用户每 30 天最多收到 1 封召回邮件。
  - 同一活动、同一用户只会收到 1 封（幂等）。
- **可控**：发送中可以暂停、继续、取消；失败自动重试 2 次；硬退信不重试，并把邮箱标为无效。
- **自动熔断**：单个活动的退信率超过 5%，或者 SMTP 返回限流或拒绝错误时，自动暂停并通知管理员。
- **发送前快照**：点击发送时冻结人群名单，避免发送过程中人群变化。
- **独立发信通道**：营销邮件可以配置**独立的 SMTP**（发件地址、服务商都可以和验证码邮件分开）；不配置时回落到系统 SMTP。这样营销邮件即使信誉受损，也不会影响验证码和密码重置邮件的送达（见第 8 节）。

### 4.5 效果统计

| 指标 | 说明 |
|---|---|
| 目标人数 / 实际发送 / 发送失败 / 退信 | SMTP 层结果 |
| 点击数、点击率 | 邮件里的链接统一经过跳转统计（不做打开像素追踪，准确率低，而且容易被判为垃圾邮件） |
| 退订数 | 本次活动带来的退订 |
| 积分领取率 | 领取了附带积分的人数占比 |
| 7 日回访率 | 发送后 7 天内登录的人数占比 |
| 14 日充值转化 | 发送后 14 天内充值的人数和金额 |
| 对照组（V2） | 自动留出 10% 不发送，用来衡量真实增量，避免把「本来就会回来」的人算成召回效果 |

## 5. 管理端页面

侧边栏新增「用户触达」分组（遵循项目现有的 TablePageLayout / DataTable 规范）：

1. **触达活动**：活动列表（状态、类别、人数、发送进度、核心转化数据）→ 新建 / 编辑 / 详情统计。
2. **人群模板**：保存的人群条件，显示实时人数。
3. **邮箱验证概览**：已验证 / 待验证 / 无效的人数和趋势（不含管理员），按「充值过 / 未充值」拆分；一键发送验证邀请；验证奖励积分数和强制档位的配置。
4. **发送设置**：营销 SMTP、限速、频控、熔断阈值、营销邮件发件人名称，以及 SPF / DKIM / DMARC 配置自检提示。

## 6. 分期

| 期 | 内容 |
|---|---|
| **V1（先做）** | `email_verified_at` / `email_invalid_at` 字段；管理员豁免；打开注册验证；用户端验证和换邮箱；验证奖励（仅充值用户）；验证邀请邮件（链接验证 + 分批 + 熔断）；手动群发活动（人群圈选 + Markdown + 变量 + 限速队列 + 频控 + 分类退订）；营销独立 SMTP；基础统计（发送、失败、退信、退订、点击） |
| V2 | 截止日期后强制验证、关键操作前提示；召回附带积分（点击领取）；7 日回访和 14 日充值转化；对照组；预置人群模板；同步站内公告；用户订阅偏好页 |
| V3 | 自动化触发（例如「充值用户连续 30 天不活跃时自动发一次召回」，作为常驻规则运行）；主题行 A/B 测试 |

## 7. 非功能与合规

- **发信信誉**：上线前检查发信域名的 SPF、DKIM、DMARC；营销邮件使用独立的子域名（例如 `news.example.com`），验证码邮件使用另一个子域名（例如 `mail.example.com`）。
- **隐私**：营销邮件只发给已验证且没有退订的用户；退订立即生效；日志中的邮箱地址做哈希（沿用现有做法）。
- **性能**：发送走后台 worker，不阻塞请求；人群计算使用带索引的字段，10 万用户规模下预估人数的耗时不超过 3 秒。
- **审计**：记录谁在什么时间对多少人发送了什么内容。

## 8. SMTP 选型建议

> 接受邮件偶尔进垃圾箱，预算敏感，优先免费/低价方案。

### 8.1 用户邮箱分布（来自开发库实测）

| 后缀 | 数量 | 占比 |
|---|---|---|
| qq.com | 1203 | ~50% |
| gmail.com | 725 | ~30% |
| 163.com | 293 | ~12% |
| outlook.com | 183 | ~8% |
| 126.com | 123 | ~5% |

约 67% 国内邮箱（QQ / 163 / 126），30% Gmail。这个分布意味着：QQ / 163 的投递质量是主要矛盾，Gmail 基本没问题。

### 8.2 域名 / DNS 准备

- **Spaceship 买的域名**：Spaceship 不提供发信服务（Spacemail 是邮箱托管，不是应用 SMTP 中继），但注册商和发信无关。
- **已托管 Cloudflare DNS**：这是最理想的起点。服务商会给 SPF / DKIM / DMARC 的 TXT 或 CNAME 记录，直接在 CF DNS 面板添加即可，和域名在哪里买无关。
- 配置顺序：先在发信服务商后台添加域名并验证 → 服务商给出 DNS 记录 → 在 CF DNS 添加 → 服务商验证通过 → 开始发信。

### 8.3 候选方案对比

| 服务商 | 免费额度 | SMTP | 付费每千封 | 评价 |
|---|---|---|---|---|
| **Brevo** | 300 封/天（约 9000/月），无月计数，无需信用卡 | 是（所有档位） | ~$1.80 | ⭐ 最灵活的免费选项，自然匹配分批发送 |
| **Resend** | 3000 封/月，每天硬上限 100 封 | 是（含免费档） | ~$0.52–0.90 | 开发者体验好，但 100/天上限太低 |
| **Amazon SES** | 沙箱期 200 封/24h；出沙箱后 $0.10/千封 | 是 | **$0.10**（最便宜） | 量大了最划算，但要先申请出沙箱 |
| **阿里云 DirectMail** | 有免费额度（需官网确认具体数额） | 是 | 按量计费 | 投 QQ / 163 最稳，国内首选 |
| **Cloudflare Email Service** | 需 Workers Paid $5/月，含 3000 封 | 是（beta 状态） | $0.35 | SMTP 仍在 beta，先观察不急用 |
| Mailgun / SendGrid | 无免费档 | 是 | $0.80–1.80 | 不考虑 |

QQ / 163 对境外发信方过滤较激进，但只要 SPF + DKIM + DMARC 配好，大部分能投递；偶尔进垃圾箱可以接受。Gmail 基本不受影响。没有一家境外服务商敢保证 QQ / 163 的投递质量，如果发现 QQ 退信明显，再考虑切到阿里云 DirectMail。

### 8.4 推荐方案

**V1 起步：Brevo 免费档**
- 300 封/天，名单约 2500 人，9 天发完一轮验证邀请
- 这个速度正好对应 PRD 的「分批发送 + 退信率熔断」设计，天然的节流，不用自己再排队
- 支持标准 SMTP，直接接入现有配置，无需改代码
- 不用信用卡，不用预付费
- 邮件进垃圾箱的概率比阿里云高一些，但可以接受

**V2 升级：Amazon SES 或阿里云 DirectMail**
- 当需要更频繁发信（例如每月发召回活动 + 资讯简报）时，Brevo 的 300/天会变成瓶颈
- Amazon SES $0.10/千封，2500 人发一轮约 $0.25，成本几乎可以忽略；新账号要先申请出沙箱，审核会问发送场景和退订机制（把 PRD 里的退订设计答上去即可）
- 如果 QQ 退信明显，切阿里云 DirectMail，国内投递最稳

**不推荐自建 SMTP**：云厂商默认封 25 端口，新 IP 没信誉容易被 QQ 直接拒收，出问题时验证码邮件也一起受影响。

### 8.5 双子域名配置

事务邮件和营销邮件使用不同的发件地址和子域名，避免营销退信污染验证码的送达信誉：

| 用途 | 建议发件地址 |
|---|---|
| 验证码、密码重置、余额通知等事务邮件 | `noreply@mail.你的域名` |
| 验证邀请、召回、资讯等营销邮件 | `hi@news.你的域名` |

在 Cloudflare DNS 里分别为两个子域名配置 SPF 和 DKIM（服务商会给具体记录）。DMARC 先加在主域名，设为 `p=none`，观察一到两周后再收紧。

### 8.6 上线前检查

- 在 Cloudflare DNS 配好 SPF、DKIM，DMARC 先设为 `p=none`
- 用 mail-tester.com 或 MXToolbox 验证配置
- 第一批验证邀请只发最近 90 天活跃的充值用户（约数百封），观察退信率
- 退信率低于 2% 后再扩大范围；退信率超过 5% 自动熔断（见 4.4）

## 9. 风险

| 风险 | 应对 |
|---|---|
| 名单从未验证过，第一次群发退信率过高，被服务商封号 | 先发验证邀请，从最近活跃的充值用户开始分批发送；退信率超过 5% 自动暂停；硬退信地址标为无效，以后不再发送 |
| 强制验证把管理员锁在外面 | 按角色豁免，强制逻辑里写死；上线前专门测试管理员登录 |
| 强制验证中断付费用户的 API 调用 | 强制只拦截网页控制台，不拦截 API |
| 换邮箱功能被用来盗号 | 换邮箱需要已登录，并要输入新邮箱收到的验证码；换绑后通知原邮箱（原邮箱有效时），并使其他会话失效（复用 `revokeEmailIdentitySessions`） |
| 验证奖励被薅 | 只发给充值过的用户，每人一次 |
| 召回积分被已经活跃的用户领走 | 人群快照在发送时冻结，只有快照里的用户能领 |
| 打开注册验证后，因为验证码邮件进垃圾箱导致注册转化下降 | 先确认 SMTP 送达质量再打开；注册页提示「没收到请检查垃圾箱」；观察开启前后的注册完成率 |

## 10. 已确认决策汇总

所有需求问题已全部确认，可进入技术设计。

| 决策点 | 结论 |
|---|---|
| 验证开关历史 | 从未开启过，所有存量普通用户均为「待验证」 |
| 上线时是否打开注册验证 | 是，同步打开 |
| 管理员豁免 | 按角色硬判定，任何档位都不拦截 |
| 充值口径 | `total_recharged > 0`，兑换码和管理员手动加余额（含线下收款）均计入 |
| 验证奖励 | 200 积分，仅限充值过的老用户，新用户不发 |
| 召回权益形式 | 积分 |
| 强制验证截止时长 | 7 天，可在后台配置 |
| SMTP 方案 | V1 先接阿里云 DirectMail（国内优先）；后续按需加 SES/Resend 覆盖 Gmail |
| 邮箱分布 | QQ 50%、Gmail 30%、163 12%、Outlook 8%、126 5% |
| 域名 / DNS | 已有自己的域名，托管在 Cloudflare，直接在 CF 配 SPF/DKIM/DMARC 记录即可 |
