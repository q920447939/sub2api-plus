# 触达中心重构方案（v2）

> 状态：已实现（2026-11-19），端到端测试 97 项通过。与本文的出入见文末「实现说明」。
> 前提：功能未上线，不做兼容；以抽象和解耦为第一目标；最后做端到端测试。

## 0. 运营要完成的一件事

> 对**某群人**，用**某种外壳 + 某段内容**，给一个**明确的行动**（可附带权益），**先小批量验证再放量**，过程中**不骚扰、不被拉黑**，最后按**这类活动该看的指标**判断有没有用。

拆出来是 7 个互相独立的概念，每个只回答一个问题：

| 概念 | 回答 | 抽象 | 变化来源 |
|---|---|---|---|
| 目的 Purpose | 这类邮件为什么发、怎么算成功 | 注册表 + 策略 | 新增业务场景 |
| 合规策略 Policy | 能不能退订、受不受频控、要求什么邮箱状态 | 值对象，由目的引用 | 法规 / 平台规则 |
| 人群 Audience | 发给谁 | 规约（Specification）组合 | 新增筛选条件 |
| 内容 Content | 说什么、长什么样 | 模板库 + 外壳库 + 变量提供者 | 运营日常 |
| 行动 Action | 用户点按钮去哪 | 解析器 + 装饰器 | 新增落地方式 |
| 权益 Benefit | 附带什么福利 | 注册表 + 策略（已有） | 新增福利类型 |
| 投递 Delivery | 怎么发、发给谁不发给谁 | 批次快照 + 台账 | 基本稳定 |
| 指标 Metric | 有没有用 | 指标规格注册表 | 新增衡量方式 |

## 1. 目的（Purpose）注册表 —— 取代写死的 `kind`

```go
type Purpose interface {
    Key() string                 // verify_email / recall / news / promo
    Label() string
    Policy() Policy              // 合规策略（见下）
    AudienceRule() Spec          // 目的自带的人群规则，如「邮箱未验证」
    Action() ActionResolver      // 主行动解析
    Metrics() []MetricKey        // 该目的关心的指标，第一个是「核心指标」
    PrimaryMetric() MetricKey
    RequiresAction() bool        // 正文是否必须含 {{cta_url}}
    Variables() []VariableProvider // 目的专属变量，如 verify_reward_points
}

type Policy struct {
    Category       string // service | marketing
    Unsubscribable bool   // 营销类 true：页脚强制带退订
    Frequency      FrequencyRule // 由「发送设置」按目的配置，取代写死的 3 天
}
```

| 目的 | 类别 | 人群规则 | 主行动 | 核心指标 | 其他指标 |
|---|---|---|---|---|---|
| 验证邮箱 | 服务 | 邮箱未验证 | 验证页（一次性邀请 token） | 验证完成率 | 点击 |
| 召回 | 营销 | 已验证 | 落地页（默认首页） | N 日回访率 | 点击、付费 |
| 资讯 | 营销 | 已验证 | 落地页，**可无按钮** | 送达（有按钮时为点击） | 退订率 |
| 活动 | 营销 | 已验证 | 落地页 | 付费转化 | 点击、领取 |

**共性**（所有目的都有，界面固定显示）：名单、已发送、失败、跳过、退订（仅营销）。
**特性**（由目的声明）：核心指标 + 其他指标。列表只显示「核心指标」一列，列名和数值都由目的给出，界面不再写死「点击」。

运营只选「目的」，合规类别由目的决定，不再让运营理解两个维度。

## 2. 人群：规约组合（已在本次修复中落地）

`segment.go` 已改为「片段自带参数 + 组合子（and / not）+ 查询组装器」。这正是 Specification 模式，v2 在此基础上：

- 每个筛选条件实现 `Spec`，并且能输出**可读描述**：`Describe() string`
- `完整规则 = 系统规则（非管理员、账号正常、邮箱有效）∧ 目的规则 ∧ 运营条件 ∧ 未退订`
- 后端返回规则描述列表，详情页显示完整规则，不再出现「人群：不限」却实际只发未验证用户的误导

资格三层（已实现）：

1. **目标人群**：上面的完整规则
2. **批次可选**：目标人群 − 正在本活动其他未结束批次排队的人 −（范围 = 只发未收到的人时）本活动已发送过的人
3. **发送时校验**：频控、状态变化（换邮箱、被封、已验证、已退订），命中则跳过并写原因

## 3. 行动：单一 `{{cta_url}}` + 解析器 / 装饰器

正文里只写 `{{cta_url}}`，删除 `verify_url` / `claim_url` / `link_url`。邮件里所有 CTA 都是跟踪链接 `/r/:token`，点击时解析：

```go
type ActionResolver interface {
    Resolve(ctx, rcpt Recipient) (target string, err error)
}
// 基础解析器（由目的提供）
verifyAction  → 生成 / 复用一次性邀请 token → /verify-email?token=…
landingAction → 活动配置的落地页（默认站点首页）
// 装饰器（由权益决定是否套上）
withClaim(inner) → /outreach/claim?t=…&next=<inner 的目标>，领完跳回落地页
```

- 附带权益时，**同一个按钮**先领取、再去落地页，不会再出现两个按钮
- 活动新增字段 `landing_url`（可选，只能是本站域名或「触达链接域名」下的地址，防止被当成跳板）
- `RequiresAction()` 为 true 或附带了权益时，正文必须含 `{{cta_url}}`；资讯类可以没有按钮
- 保存时校验未知变量：模板里出现当前目的 + 权益不提供的变量，直接报错，不再原样保留进邮件

## 4. 内容分层：外壳库 + 模板库 + 变量提供者

```
邮件 = 外壳(Layout) ⊕ 正文(Template 渲染结果) ⊕ 合规区(系统强制)
```

### 4.1 外壳（Layout）—— 新增「邮件外壳」页面，增删改查

由运营配置的**块**组成，不开放自由 HTML（邮件客户端兼容性差，且容易误删合规内容）：

| 块 | 可配置项 |
|---|---|
| 页头 | 无 / 站点名文字 / Logo 图片 + 链接；主题色 |
| 版式 | 卡片式（当前）/ 通栏纯文本；内容宽度 |
| 页脚品牌区 | Markdown（版权、联系方式、社媒链接），支持 `{{site_name}}` 等变量 |
| 合规区 | **不可编辑**，系统按目的的 Policy 自动追加：营销 →「为什么收到 + 退订链接」；服务 →「这是与账号相关的服务邮件」 |

- 可以有多个外壳，设一个为默认；回答「一定是上下结构吗」：结构由版式块决定，可选，但合规区始终存在且位置固定
- 删除外壳前检查是否被模板引用

### 4.2 模板库（Template）—— 新增「邮件模板」页面，增删改查

| 字段 | 说明 |
|---|---|
| 名称、适用目的 | 一个模板只服务一个目的（变量集合由目的决定） |
| 主题、正文 Markdown | |
| 外壳 | 可选，空 = 默认外壳 |
| 内置标记 | 系统预置的 4 个起始模板，可编辑可复制，不可删除 |

- 新建活动：选目的 → 选模板 → **复制**内容到活动（活动可以继续改，不影响模板；页面显示「源自模板 X」）
- 和批次快照同一个原则：改模板不影响已有活动，改活动不影响已有批次
- 前端 `TEMPLATES` 常量删除，模板全部来自后端

### 4.3 变量提供者（VariableProvider）—— 组合模式

```go
type VariableProvider interface {
    Docs() []VariableDoc
    Resolve(ctx, rc RenderContext) map[string]string
}
```

用户变量（username/email/balance/last_active_days）、站点变量（site_name）、行动变量（cta_url/unsubscribe_url）、目的变量（verify_reward_points）、权益变量（reward_points）各自是一个提供者。编辑器的变量列表 = 当前目的 + 已选权益的提供者合集；渲染时同样合并。删除 `Vars.lookup` 里的 switch。

### 4.4 渲染管线（模板方法）

`变量替换 → Markdown → 外壳(版式/页头/页脚品牌区) → 合规区`。编辑器预览、批次逐人预览、测试邮件、实际发送全部走同一条管线（现在测试邮件是另一条路径）。

批次快照增加外壳快照：生成批次时冻结「内容 + 外壳」，保证预览所见即发出。

## 5. 投递

- 选人范围：只发未收到的人（默认）/ 再发一轮（**本次已实现**）
- 同一时间只执行一个批次（共用 SMTP 额度），保持
- 频控按目的配置（发送设置里按目的列出），删除写死的「验证邀请 3 天」
- **直发（Direct send）**：对单个用户立即发送某目的的邮件，不建活动，台账记 `campaign_id = NULL`。用于：
  - 邮箱验证页「给此用户发验证邀请」
  - 测试邮件：**发给管理员自己，但用选定真实用户的数据渲染**（现在只能用示例数据）

## 6. 验证邀请收敛（决策 5）

现在有两条发送路径（邮箱验证模块自己拼邮件 / 触达中心批次），模板和链接域名都不一致。收敛为：

```
emailverify：只负责「验证」这个领域 —— 发 token、消费 token、标记已验证、发奖励
outreach   ：负责「发邮件」—— 模板、外壳、链接、限速、台账
```

- emailverify 暴露 `InviteIssuer` 端口（已有），outreach 的「验证邮箱」目的用它生成 token
- emailverify 管理端的单发邀请改为调用 outreach 的直发能力；为避免包循环，emailverify 只依赖一个 `InviteMailer` 接口，由 `plus_routes.go`（组合根）注入 outreach 的实现
- 删除 emailverify 里自带的邀请邮件模板和 `sendInviteMail`

## 7. 页面职责

| 页面 | 职责 | 操作 |
|---|---|---|
| 活动列表 | 管理「定义」 | 行内：编辑、复制、删除；列：名称、目的（+权益）、批次数/执行中、累计发送、**核心指标**、创建时间（到分钟） |
| 活动详情 | 「运营」这个活动 | 主操作：生成批次；完整人群规则；按目的的指标卡片；批次列表。编辑/复制/删除收进「更多」 |
| 活动编辑 | 定义 | 已有批次时顶部提示「修改只影响之后生成的批次」 |
| 批次详情 | 执行与核对 | 开始/暂停/恢复/取消/删除；逐人预览；跳过原因 |
| 邮件模板 | 内容资产 | 增删改查、预览（选外壳、选样例用户） |
| 邮件外壳 | 品牌 | 增删改查、设为默认、预览 |
| 发送设置 | 投递规则 | 限速、按目的的频控、熔断、统计窗口、链接域名、批次保留 |
| 邮箱验证 | 验证领域 | 概览、奖励积分、邀请有效期；单发邀请走直发 |

侧边栏：触达中心 → 活动 / 模板 / 外壳 / 发送设置。

## 8. 代码结构

```
internal/plus/outreach/
├── module.go            组合根：注册目的、权益、变量提供者、指标
├── purpose/             Purpose 接口 + 注册表 + 4 个实现
├── audience/            Spec 组合子、查询组装器（由现 segment.go 演进）
├── content/             Layout / Template 仓储、渲染管线、VariableProvider
├── action/              ActionResolver + withClaim 装饰器
├── benefit/             现 benefit.go 迁入
├── metric/              MetricSpec 注册表：key、label、SQL 片段、分母

└── handler.go           HTTP 只做参数解析与错误映射
```

依赖方向：`handler → delivery → {purpose, audience, content, action, benefit, metric}`，下层互不依赖，全部通过接口。

## 实现说明（与上文的出入）

- **代码结构**：没有拆子包，仍是单个 `outreach` 包，按概念一文件一职责：`purpose.go`、`action.go`、`variables.go`、`metric.go`、`content.go`（外壳 / 模板）、`render.go`（渲染管线）、`segment.go`（人群规约）、`service.go`、`repository.go` / `repo_send.go`、`worker.go`。拆子包会迫使 `DBTX`、输入错误、SQL 片段等共用类型再挪进一个公共包以避免循环引用；解耦靠接口与注册表，而不是目录。
- **台账**增加 `category` 列（service / marketing），跨目的的营销频控只看它，不需要认识具体目的。
- **收件人**增加 `purpose` 列；直发（如单发验证邀请）的收件人与台账 `batch_id` / `campaign_id` 为空。
- **测试邮件**仍只发给操作者自己，可选「用某个用户的真实数据渲染」。
- **路由**：活动放在 `/admin/outreach/campaigns`，`/admin/outreach` 重定向过去。侧边栏按前缀高亮，活动放根路径会让模板 / 外壳 / 设置页也高亮「触达活动」。
- **前端测试**：没有做 Playwright；页面经过 vue-tsc 与 eslint，主路径由接口级 E2E 覆盖。

## 边界调整（2026-11-19 第二轮）

每个配置项和数据只归一个模块：

| 内容 | 归属 | 说明 |
|---|---|---|
| 链接域名、限速、频控、熔断、批次保留 | 触达中心 · 发送设置 | `outreach.DeliveryConfig`，只剩投递规则 |
| 回访 / 付费统计窗口 | 目的 | 指标定义的一部分（如「7 日内回访」），不可在设置里改，保证活动之间可比 |
| 权益领取有效期 | 活动 | `claim_days`，生成批次时冻结 |
| 验证奖励、验证链接有效期、站内提醒间隔 | 邮箱验证 · 设置 | `emailverify.Config` |
| 效果指标 | 活动 | 批次只看投递结果（发送 / 失败 / 跳过 / 退信） |

- **配置存储**：`plus_settings` 表，每个模块一行（`plusconfig.Store[T]`，泛型 + 乐观锁），模块之间不共享配置结构。旧的 `mailsettings` 包已删除。
- **验证状态绑定邮箱**：`plus_email_verifications` 每个「用户 × 邮箱」一行。已验证 = 当前邮箱有记录；换邮箱后自动回到待验证，不需要感知上游的换邮箱流程。
- **上游钩子**：`service/plus_email_verified_hook.go`，在注册（填了验证码）、第三方登录注册、绑定 / 更换邮箱成功后回调，记录来源。
- **站内提醒**：服务端判断（`status.remind`），关闭后按设置天数暂停，换设备一致；不做邮件自动重发。
- **依赖方向**：触达中心只通过端口使用邮箱验证（签发 token、读奖励积分、标记无效）；邮箱验证不认识活动和批次。
- **管理端「邮箱验证」**：概览 / 验证记录 / 设置 三个标签页。
- **迁移重新编号**：264 `plus_settings`、265 `plus_email_verify`、266 `plus_outreach`（未上线，不兼容旧编号）。
