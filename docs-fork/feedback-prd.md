# 用户反馈中心：产品需求文档 v1.3

> 状态：需求已确认，待技术设计
> 代码位置（规划）：后端 `backend/internal/plus/feedback`，前端 `frontend/src/plus/feedback`

## 0. 一句话定位

**反馈中心是一个「问题和建议的沉淀与分析系统」，不是客服工单系统。** 急事走售后群，马上解决；不急的问题、模糊的问题和改进建议进入反馈中心，管理员有空时处理，统一记下来做分析，作为产品改进的依据。

## 1. 反馈中心在整体运营中的位置

### 1.1 价值闭环

```
 ① 遇到问题/想法 ──→ ② 提交（选场景 + 自动采集）──→ ③ 分拣（定级、标签、追问）
        ↑                                                      │
 ⑦ 用户感知到改进 ←── ⑥ 产品迭代 ←── ⑤ 数据分析 ←── ④ 处置（解决/采纳/不处理）+ 回复 + 积分
```

| 环节 | 现在缺什么 | 反馈中心补上什么 |
|---|---|---|
| ② 提交 | 群里一句话，缺少上下文 | 按场景引导填写，并自动带上页面、环境、账号快照 |
| ③ 分拣 | 靠管理员记在脑子里 | 严重等级、标签、追问对话 |
| ④ 处置 | 处理完就散了 | 有结论、有回复、有积分，可以回溯 |
| ⑤ 分析 | 只有体感 | 从场景、严重度、用户三个视角出看板 |
| ⑦ 回馈 | 用户不知道提了有没有用 | 站内红点、处理结论、积分，让用户愿意继续提 |

### 1.2 与售后群分工

| | 售后群 | 反馈中心 |
|---|---|---|
| 适合什么 | 紧急、阻塞、要马上处理的事 | 不急的问题、需要说清楚的问题、建议 |
| 时效 | 实时 | 异步，不承诺响应时间 |
| 产出 | 当下把问题解决 | 可以统计、可以回溯的数据 |

提交页顶部显示后台配置的 Markdown 公告（见 4.5），用来写「紧急问题请直接联系售后群」和群链接或二维码。售后群里的问题**不补录**进系统。

### 1.3 与现有模块的关系（复用，不重复造）

| 现有能力 | 在反馈中心里的用途 |
|---|---|
| `plus/points` 积分账本 | 发放反馈奖励（新增来源 `feedback_reward`） |
| `ops_error_logs`（带 user_id 和时间索引，见 `migrations/148_*`） | 管理员查看详情时，自动列出该用户提交前后的错误请求（用户端看不到错误请求，不对用户开放） |
| 订单、订阅数据 | 充值类反馈自动带出近期订单 |
| 渠道状态、模型智商检测 | 模型效果类反馈旁边显示同时段的客观数据（V3） |
| 侧边栏的 plus 菜单机制 | 用户端「我的反馈」和管理端「反馈管理」两个菜单项，都带红点 |

## 2. 目标与衡量指标

| 目标 | 指标 |
|---|---|
| 收得上来 | 每周新增反馈数；按场景引导填写的补充信息完整率 |
| 处理得掉 | 待处理积压数；平均处理时长（只观察，不考核） |
| 看得明白 | 每月能产出「问题最集中的 Top 场景」和「建议 Top 列表」 |
| 用户愿意提 | 提交过反馈的用户占活跃用户的比例；二次提交率；获奖反馈占比 |

## 3. 角色与权限

| 角色 | 能做什么 |
|---|---|
| 普通用户（必须登录） | 提交反馈、查看自己的反馈、在未结案时补充信息、关联自己的上一条反馈 |
| 管理员 | 查看全部反馈、回复、追问、内部备注、定级、打标签、修正场景、结案、发积分、标记重复、看看板、改配置 |

不新增角色（不做客服/运营子账号），不支持匿名提交。

## 4. 核心概念

### 4.0 反馈类型（用户必选，第一步）

| 类型 | 含义 | 可选结论 | 积分 |
|---|---|---|---|
| 🐞 **问题** | 用不了、出错了、不明白怎么用 | 已解决 / 不处理 / 重复 | **不发** |
| 💡 **建议** | 想要新东西、希望改进 | 已采纳 / 不处理 / 重复 | 已采纳时可发 |

- **场景从属于类型**：问题和建议各有一套场景，用户先选类型，再在该类型下选场景（见 4.1）。
- 管理员可以修正类型和场景（例如用户把建议提成了问题）。用户原选和修正后的都保留，统计和积分按修正后的值。

### 4.1 反馈场景

**原则：用用户的话问「你在做什么时遇到了什么 / 想要什么」，不要求用户懂系统有哪些模块。** 场景只有一级，用卡片展示，每个场景有自己的引导文案和补充字段。

**问题类场景**

| 场景卡片 | 典型情况 | 补充字段（选填） |
|---|---|---|
| 🔌 **接入和配置** | 不会配 Claude Code、Cursor 等客户端，Key 和地址不知道怎么填 | 使用的客户端 |
| ⚠️ **调用报错** | 报错、超时、请求中断、没有响应 | 大概时间、模型、错误提示原文 |
| 🧠 **模型效果不对** | 回答变差、疑似降智、模型不对、画图效果差 | 模型 |
| 🐢 **速度慢或不稳定** | 很慢、时好时坏、某个渠道用不了 | 模型或分组 |
| 💳 **充值和扣费** | 充值没到账、扣费有疑问、订阅或套餐问题 | 订单号 |
| 🎁 **活动和权益** | 签到、积分、九宫格、兑换码、邀请返利 | — |
| 👤 **账号和登录** | 登录、绑定、改资料、安全 | — |
| 💬 **其他问题** | — | — |

**建议类场景**

| 场景卡片 | 典型情况 | 补充字段（选填） |
|---|---|---|
| ✨ **想要新模型** | 希望接入某个模型、分组或渠道 | 模型名称 |
| 🧩 **想要新功能** | 现在做不到、希望能做到的事 | 期望的效果 |
| 🎯 **体验可以更好** | 页面、流程、交互不顺手 | 期望的效果 |
| 🏷️ **价格和套餐** | 计费方式、套餐组合、充值档位 | — |
| 🎉 **活动和福利** | 新玩法、奖励规则 | — |
| 💬 **其他建议** | — | — |

配套规则：

- **自动预选**：用户从某个页面打开反馈时，按页面路由预选场景，用户可以改。例如在充值或订单页打开预选「充值和扣费」，在积分乐园打开预选「活动和权益」。
- **管理员可以修正场景**：用户选的场景和管理员修正后的场景都保留。统计用修正后的；两者不一致的比例用来判断场景文案是否让人看不懂。
- **场景可以配置**：后台可以按类型增删、排序、停用，修改文案和补充字段（单行文本 / 多行文本 / 下拉 / 时间）。每个场景有一个固定的 key，改名不影响历史统计。
- **更细的区分交给标签**：比如「Claude 分组」「支付宝」「流式中断」，由管理员在处理时添加，不让用户选。

### 4.2 严重等级（只由管理员判定，用于分析）

四档：**严重 / 一般 / 轻微 / 无效**，问题和建议共用。

| 档位 | 问题类 | 建议类 |
|---|---|---|
| 严重 | 无法使用，或涉及资金损失 | 很多人提过，价值很高 |
| 一般 | 影响体验，但能绕过 | 有价值，可排进计划 |
| 轻微 | 体验小瑕疵 | 锦上添花 |
| 无效 | 不是问题或误解 | 不采纳 |

严重等级只用来排优先级和做分析，**和积分没有关系**。

### 4.3 积分奖励（只奖励建议）

- **只有类型为「建议」、结案为「已采纳」时**，管理员才能打开「发放积分」开关。问题单在任何结论下都不发积分，结案弹窗里不出现这个开关。
- **默认 500 分，每档加减 100**，也可以手动输入其他数值。
- 每条反馈最多发一次，发放幂等（不会重复入账）。通过 points 模块记账，来源记为 `feedback_reward`，关联反馈 ID。
- 不设上限，不和严重等级挂钩，由管理员判断这条反馈有没有价值。
- 积分模块未启用时，自动隐藏这个开关。

### 4.4 状态

| 状态 | 含义 | 谁可以设置 |
|---|---|---|
| 待处理 | 新提交，或用户刚补充过 | 系统 |
| 待补充 | 管理员追问了，等用户回复 | 管理员（发送追问时自动切换） |
| **已解决** | 问题已修复，或咨询已答复 | 管理员 |
| **已采纳** | 建议被接受 | 管理员 |
| **不处理** | 无效、无法复现或信息不足（必须填原因） | 管理员，或系统超时自动关闭 |
| **重复** | 和另一条是同一件事（必须关联主反馈） | 管理员 |

「已解决」只用于问题，「已采纳」只用于建议。

### 4.5 反馈中心公告（后台配置，Markdown）

- 管理员在配置页用 Markdown 编辑一段公告，带实时预览和开关。
- 显示在「提交反馈」页和「我的反馈」列表顶部，可以折叠。
- 售后群提示、群链接或二维码、近期根据反馈做的改进，都写在这段公告里，不再单独做「售后群提示」配置项。
- 渲染时只支持标准 Markdown（标题、列表、链接、图片、加粗、代码），不渲染原始 HTML，防止 XSS。
- 公告更新后，用户端「我的反馈」不额外亮红点，只在页面内显示。

## 5. 状态流转与规则

```
             管理员追问
   待处理 ──────────────→ 待补充
     ↑                       │  ├─ 用户回复 → 回到「待处理」
     └───────────────────────┘  └─ 超过 N 天未回复 → 「不处理：信息不足」（系统自动）

   待处理 / 待补充 ──管理员结案──→ 已解决 / 已采纳 / 不处理 / 重复   （终态）
```

1. **待补充的超时**：管理员可以随时手动结案；系统每天检查一次，超过 N 天（默认 7 天，可配置，0 表示关闭）没有回复的，自动结案为「不处理：信息不足」，并在时间线写一条系统事件。
2. **终态后锁定对话**：用户想继续，就提一条新反馈并勾选「关联上一条」，两条在双方时间线里互相链接。
3. **重复**：被标为重复的反馈显示「已合并到 #123」。主反馈统计「影响人数」= 主反馈 + 合并进来的条数。积分一般只发给主反馈，管理员也可以给重复的单独发。
4. **只能追加，不能修改**：用户的原文和补充都不能修改或删除。
5. 所有状态变化、定级、改场景、发积分都写进事件记录（谁、什么时间、改了什么）。
6. 不承诺响应时间，不需要用户确认关闭，不分派负责人——这是与工单系统的区别。

## 6. 用户端

### 6.1 入口

- **侧边栏「我的反馈」**：有未读的管理员回复或状态变化时显示红点。
- **全局悬浮的「反馈」小按钮**：后台可以关闭。点开时自动带上当前页面，用来预选场景。

### 6.2 提交流程（一屏完成）

1. 顶部：反馈中心公告（Markdown，后台配置）。
2. 选择类型：问题 / 建议（必选）。
3. 选择场景（卡片，必选）。
4. 描述（必填，10 到 2000 字），输入框提示文字随类型和场景变化。
5. 补充字段（选填），按场景显示。
6. 截图，最多 3 张，每张不超过 5MB；提醒「请勿截到 API Key 明文」。
7. 可选「关联我的上一条反馈」。
8. 提交。

**系统自动采集（用户不可见）**：当前页面、浏览器和系统、前端版本、IP、提交时间，以及账号快照（余额、有效订阅、所在分组）。

**防刷**（均可配置）：每人每天最多 10 条；两次提交至少间隔 60 秒；同一用户同时处于「待处理」或「待补充」的反馈最多 5 条。

### 6.3 我的反馈

- **列表**：类型、场景、描述摘要、状态、最后更新时间、未读标记；可按状态筛选。
- **详情时间线**：原始提交、我的补充、管理员回复和追问、状态变化、积分发放。不显示内部备注。
- **未结案时**：底部补充输入框（文字 + 图片）。处于「待补充」时高亮提示「管理员需要你补充信息」。
- **结案后**：显示结论；建议被采纳且发了积分时显示所得积分，并提供「提一条新反馈并关联」按钮。

## 7. 管理端

### 7.1 反馈列表（菜单「反馈管理」，红点显示待处理数量）

- 默认视图：待处理，按最近活动时间倒序（用户刚补充过的排最前）。
- 筛选：类型、状态、场景、严重等级、标签、用户、时间段、是否有图、是否发过积分。
- 批量操作：定级、打标签、结案。
- 导出 CSV。
- 新反馈只通过菜单红点提示，不做邮件/机器人推送。

### 7.2 详情工作台

| 左侧：对话时间线 | 右侧：上下文面板 |
|---|---|
| 用户原文、补充、截图 | **用户卡片**：账号、注册时间、余额、订阅、历史反馈数和获奖数，链接到用户详情 |
| 管理员回复、追问 | **自动采集信息**：页面、浏览器、版本、账号快照 |
| 内部备注（黄色底，用户看不到） | **错误请求**：该用户提交前 24 小时到提交后 1 小时内的 `ops_error_logs`（错误码、模型、分组、摘要，可展开） |
| 系统事件 | **场景相关数据**：充值类显示近期订单；调用、速度、模型类显示对应分组当时的渠道状态（V3） |
| | **关联反馈**：上一条反馈、重复反馈 |

底部操作栏：

- 回复：不改变状态
- 追问：状态变为「待补充」
- 内部备注
- 定级、打标签、修正类型和场景
- **结案**：结论选项随类型变化（问题：已解决/不处理/重复；建议：已采纳/不处理/重复）；填原因或关联主反馈；**仅建议单选「已采纳」时**出现积分开关（默认 500，每档 100）；可附一句给用户的话

### 7.3 分析看板

| 视角 | 内容 | 回答什么问题 |
|---|---|---|
| **场景视角** | 各场景数量和趋势；场景 × 类型（问题/建议）；场景 × 结论 | 用户最常在哪里卡住 |
| **严重度视角** | 严重度 × 场景热力图；严重、一般两档的积压数 | 哪里最痛、该先修什么 |
| **用户视角** | 用户排行：反馈总数、问题/建议数、各场景占比、被解决/采纳数、有效率、累计积分；点进用户看场景分布饼图和反馈列表 | 谁是高质量反馈者，谁总在同一处遇到问题 |
| **建议池** | 类型为「建议」的按影响人数和严重度排序，标注是否已采纳 | 直接当产品待办列表用 |
| **趋势和效率** | 每日新增和结案数；平均处理时长；超时自动关闭占比 | 处理能力够不够；追问是不是常没人回 |

时间范围可选 7 / 30 / 90 天或自定义。所有图表可点进去，跳到筛选好的反馈列表。

### 7.4 配置项

总开关、悬浮按钮开关、反馈中心公告（Markdown + 开关）、场景列表（文案、图标、补充字段、自动预选的页面规则）、防刷三个阈值、附件数量和大小、待补充超时天数、积分默认值和步长、回复模板（V2）。

## 8. 数据模型草案

| 表 | 关键字段 |
|---|---|
| `plus_feedback` | id、user_id、type_user、type_final（issue/suggestion）、scenario_user、scenario_final、content、extra（场景补充字段，JSON）、context（自动采集信息，JSON）、status、severity、tags、close_reason、merged_into_id、prev_feedback_id、reward_points、reward_ledger_id、user_unread、last_activity_at、created_at、closed_at |

- 迁移文件按顺序编号（当前最新为 `255_plus_channel_status.sql`，预计 `256_plus_feedback.sql`，落地时以实际最新编号为准）。
- 附件存本地数据卷 `data/plus/feedback/YYYY/MM/<uuid>.<ext>`，**通过鉴权接口读取**，不作为公开静态文件。只允许图片格式，上传时去掉 EXIF。

## 9. 接口清单（`/api/v1/plus`）

| 端 | 接口 |
|---|---|
| 用户 | `GET /feedback/meta`（场景和配置）· `POST /feedback` · `GET /feedback` · `GET /feedback/:id` · `POST /feedback/:id/messages` · `POST /feedback/attachments` · `GET /feedback/attachments/:id` · `GET /feedback/unread` |
| 管理 | `GET /admin/feedback` · `GET /admin/feedback/:id`（含上下文面板）· `POST /admin/feedback/:id/messages` · `PATCH /admin/feedback/:id`（定级、标签、类型、场景）· `POST /admin/feedback/:id/close` · `POST /admin/feedback/batch` · `GET /admin/feedback/stats` · `GET /admin/feedback/pending-count` · `GET/PUT /admin/feedback/config` · `GET /admin/feedback/export` |

后台任务：每天运行一次，处理待补充超时自动关闭，复用现有 plus 模块的 worker 写法。

## 10. 非功能要求

- **隐私**：不存 API Key 明文，只存 key_id；错误日志面板只给管理员看；内部备注只在管理端接口返回。
- **权限**：用户端所有查询强制带 `user_id = 当前用户`，附件读取校验归属。
- **不改动上游**：代码放在 `backend/internal/plus/feedback` 和 `frontend/src/plus/feedback`，接入点用 `// [plus]` 标注。
- **国际化**：所有固定文案进 locale 文件；场景文案来自后台配置，不进 i18n。

## 11. 分期

| 阶段 | 范围 | 交付价值 |
|---|---|---|
| **MVP** | 类型 + 场景化提交、反馈中心公告（含补充字段、自动采集、截图）、我的反馈和时间线、补充信息、管理端列表和详情、回复、追问、内部备注、定级、标签、结案、积分、双端红点、待补充超时关闭、基础配置 | 收集、处理、回馈的闭环跑通 |
| **V2** | 详情页错误请求面板和订单面板、标记重复和影响人数、完整分析看板（三个视角加建议池）、导出、回复模板、关联上一条反馈 | 排查更快，开始用数据做决策 |
| **V3** | 渠道状态和智商检测数据联动、改进播报（在公告中人工撰写，后续可做模板）、「已采纳」建议上线后批量通知、用自家网关模型给反馈做摘要并推荐场景和标签 | 反馈驱动产品，并让用户看到 |

## 12. 风险和未定事项

| 项 | 说明 | 当前处理方式 |
|---|---|---|
| 为了积分灌水 | 积分不设上限 | 人工审核把关；用户视角能看出低有效率用户；必要时再加限制 |
| 用户把急事提到反馈中心 | 没有响应时效 | 提交页顶部公告写明售后群入口 |
| 场景文案让人看不懂 | 用户选错场景 | 两个场景字段都保留，看修正率再调整文案 |
| 「已采纳」之后的跟进 | 已采纳不代表已上线 | MVP 不做，V3 用「上线通知」补上 |

## 附：已确认的决策

- 定位为反馈箱 + 轻量对话，不做工单（无 SLA、无用户确认关闭、无分派）。
- 只有登录用户可提交；角色只有普通用户和管理员。
- 售后群问题不补录；管理端只用菜单红点提示。
- 分类：类型（问题/建议，必选）+ 使用场景（一级卡片，必选），细分用管理员标签。
- 待补充超时：管理员手动关闭 + 系统 N 天自动关闭，两者都做。
- 积分：只奖励被采纳的建议，问题单不发；默认 500，步进 100，不设上限，与严重等级无关。
- 反馈中心公告：后台配置 Markdown，显示在提交页和我的反馈页顶部。
- 附件存本地数据卷。
- 功能建议公开投票暂不做。

## 附：v1.3 调整（2026-11-16，以本节为准，覆盖上文对应描述）

- **去掉「重复」结论**：结案只有「已解决 / 不处理」（问题）和「已采纳 / 不处理」（建议）。历史上已标为重复的数据仍能显示。
- **「追问」并入「回复」**：管理员只有「回复用户」和「内部备注」。回复后状态变为 **已回复**（原「待补充」），用户补充后回到「待处理」；已回复超过 N 天用户没回应，自动结案为「不处理」。
- **去掉「预选页面」**：提交时不再按页面预选场景，也不再记录所在页面；详情页「提交环境」只显示浏览器、站点版本、IP、当时余额。
- **管理端查询**：内容、用户（邮箱 / 用户名 / ID）、反馈 ID 三个独立搜索框，均为模糊匹配；用户详情链接到「反馈处理」时按用户筛选。
- **场景编辑**：图标可选择；场景和补充字段的标识自动生成，管理员不再填写；下拉字段的选项回车添加。
- **公告**：带格式工具栏的 Markdown 编辑器，宽屏左右实时预览，渲染沿用项目公告的 Markdown 样式。
