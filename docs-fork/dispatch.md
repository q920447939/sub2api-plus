# 上游调度台（plus/dispatch）

同一平台、同一分组下接了多个上游号池。调度台解决两件事：

1. **上游不再是黑盒**：每个账号是不是声称的模型、有没有降智、稳不稳、快不快、会不会被限流，都有结论、有依据、能对比、能回看。
2. **看完就能就地调整**：在调度台里直接暂停或降低某个账号在某个分组的份额，调整前给预计值，调整后有效果对比。以后的程序 / AI 自动调度走同一个入口。

只给管理员用，菜单在「上游调度台」：健康总览、指标对比、检测记录、异常待处理、调度调整、检测配置、操作日志。

## 概念（七层）

| 层 | 是什么 | 在哪改 |
|---|---|---|
| 维度 | 模型身份、智力、稳定、速度、容量、成本…，带「作用」：门槛 / 参与调度 / 仅展示 | 检测配置 → 维度（可新建、排序、停用） |
| 检测方式 | 检测的办法，代码插件：流量统计、模型指纹识别、判分题、存档题、账号属性 | 代码：`detector_*.go`，在 `module.go` 里注册 |
| 检测项 | 某个类型的一个实例（糖果题 = 判分题 + 题面 + 答案），**判定规则在这里** | 检测配置 → 检测项 |
| 检测计划 | 主动检测项 × 一个平台 × 若干模型 × 账号范围 × 频率（每 N 分钟） | 检测配置 → 检测计划 |
| 立即体检 | 对单个账号直连测一轮，不受计划和流量限制 | 健康总览 / 账号诊断详情 →「立即体检」 |
| 检测记录 | 每一次账号直连检测（题面快照、回答、判分） | 检测记录 |
| 判定 | （分组 × 账号 × 模型 × 检测项）的结论；维度结论 = 下面最差的检测项 | 每 5 分钟自动评估，也可「重新诊断」（记进操作日志） |
| 使用方 | 待处理、调度建议、调度调整（钩子） | 待处理 / 调度调整 |

检测对象是「账号 × 模型」。

**账号范围**（多选，命中任意一条就测；规则在 `scope.go` 注册，页面按声明渲染）：有流量的账号（流量占比 ≥ x%）、新接入的账号（创建 N 天内，没流量也测）、指定账号。另可排除账号，排除优先。计划不支持改题，题目只在检测项上维护。

**新账号 / 先试再放量**：账号刚建好还没有流量时，总览里标「新接入」，可以直接点「立即体检」选检测项和模型测一轮；结果照常判定（判定依据里注明「来自手动体检，没有计划定期复测」），7 天内有效。确认没问题再放量。同一个凭证（地址 + Key 相同）只测一次，结果在所有分组共用；流量指标按分组分别统计。

## 判定

- **流量统计**：从 `usage_logs` / `ops_error_logs` 汇总到 `plus_dispatch_traffic_hourly`（每 5 分钟重算最近两小时），「现在」取最近 60 分钟滚动值。和参照比：参照按回退链取第一个可用的——同组同模型其他账号 → 全站同平台同模型其他账号 → 自己过去 7 天同一时段 → 固定值；可比的少于 N 家（默认 1）就换下一个；报错率 / 限流率最后按绝对值兜底。有数据但没有任何参照时显示「无参照」和当前值，不算「数据不足」。超过阈值并持续 T 分钟才算。用户侧错误（余额不足等）和 429 不算报错；429 单独算「限流率」。
- **模型指纹识别**：lm-detector（MIT）出 3 道随机整数题，用我们自己的多协议客户端直连账号发请求（所以 Gemini 原生协议也能测），再用 SDK 打分。连续 N 次识别成别的模型判异常；置信度低的不计入。参考库按模型版本收录，库里没有的模型在计划里置灰。参考库首次使用时从 lm.ikale.io 下载（约 3.6 MB），缓存在 `/app/data/plus_lmfpd/`。
- **判分题**：近 N 次答对次数，固定阈值或和同组其他账号比。判分方式：数值相等 / 完全一致 / 包含 / 正则；多个答案命中任一个就算对。
- 请求出错不计入判定；同一项连续出错 N 次进待处理「检测请求连续失败」。

账号直连时按账号自己的模型映射换算模型名，和网关实际发出去的一致。

## 调度调整与执行层

- 调整是「分组 × 账号」的**当前状态**：正常 / ×系数（0~1）/ 暂停。一直有效，直到下一次调整覆盖（不分人工、采纳建议还是以后的自动）。每次变化写调整历史 + 操作记录。
- 执行层是上游选号代码里的钩子（`service/plus_dispatch_hook.go`）：在「候选账号列表」这一层改名单，和后面各平台用什么算法挑号无关，所以 Claude / OpenAI / Gemini 全部通用。
  - 暂停：从候选里拿掉，粘性会话也换号。
  - ×系数：每次按 1 − 系数的概率拿掉；**已粘住的会话不受影响**（保住缓存），所以效果会逐步出现。
  - 名单被拿空时原样放行；同组至少留一个没被暂停的账号（保存时校验）。
- 档位：关闭 / 只观察 / 人工调整。只有「人工调整」档钩子才介入；其他档调整保留但不生效。热路径零 IO：规则表每 10 秒从库里整体刷新（本实例改动立即刷新）。
- 不改账号表任何字段。账号列表上显示「调度台：已暂停 / ×0.3」标签。
- 效果对比：每 10 分钟的份额堆叠图（竖线 = 调整时刻）、分组整体前后对比、接收方扛不扛得住、钩子介入次数。
- 依据消失提醒：账号各维度恢复正常满 N 小时还被压着，提示「建议恢复」。

## 调度建议（不积极）

以实际份额为起点，只从可疑 / 异常的账号挪走，正常的按现有份额接收；数据不足的不动。门槛维度异常按维度上的「确认前 / 确认后」设置处理；参与调度的维度按系数。护栏：被降的至少保留 x%，每小时最多挪 y%，本组没有正常账号可接时不挪。每条建议都能一键采纳（生成一次调整）。

## 扩展

- 新检测办法：实现 `Detector`（被动）或 `ActiveDetector`（主动），在 `Spec()` 里声明能力（是否发请求、单次结果枚举、计划字段），在 `module.go` 注册。页面、计划表单、判定、调度都不用改。
- 新维度 / 新题目：后台配置，不用写代码。
- 自动调度 / AI：读判定、建议和调整历史，调用同一个 `AdjustService.Apply`（source 换成 auto / ai）。
